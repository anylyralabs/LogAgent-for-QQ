# Agent 应用构建工作流 —— 学习笔记

> 整理时间：2026-10-15 ｜ 用途：为 logagent-for-qq（日志分析 Agent）规划提供方法论基础

## 1. 基本概念：Workflow vs Agent

- **Workflow（工作流）**：LLM 调用沿**预定义路径**编排，步骤是确定的。
- **Agent（智能体）**：LLM 在循环中**自主决定**下一步动作（调用什么工具、何时结束）。

> 核心原则：**能用 workflow 解决的不要上全自主 agent**。大多数问题只需要 workflow + 少量 agent 步骤。

## 2. 六大核心模式

### 2.1 ReAct（Reason → Act → Observe）
紧密的"思考–工具–观察"循环，每步依赖上一步结果。
- **适用**：路径未知的开放式任务（API 调用、搜索、交互式排查）。
- **优点**：简单、可追踪、延迟可控。**注意**：长任务有 token 漂移风险。

### 2.2 Plan-and-Execute（先规划后执行）
先产出完整计划，再逐步执行，失败时重规划（replan）。
- **适用**：步骤可预先确定的复杂任务（报告生成、深度日志分析）。
- **优点**：规划器只跑一次，减少反复决策的成本和漂移。

### 2.3 Reflection（反思/自我批判）
生成 → 对照成功标准批判 → 修订，循环直至通过。
- **适用**：结果可校验的高价值任务（代码、分析结论）。
- **代价**：延迟和成本换质量。**生产中这是提升质量杠杆最大的单一模式**。

### 2.4 Tool Use（工具调用）
一切 agent 的基座。质量取决于**工具 schema 的描述质量**，往往比模型选择更重要。
- 工具描述要写清"什么时候用"，不只是"做什么"；
- 每个插件 3–7 个相关函数，过多会迷惑模型；
- 返回**结构化类型**而非自由文本；
- 永远不要信任模型输出做安全决策，校验在工具侧完成。

### 2.5 Agentic RAG（智能体化检索增强）
检索本身变成 agent 可反复调用的工具：改写查询 → 选择来源（向量库/网页/结构化API）→ 评估中间结果 → 判断上下文足够才生成，产出带引用的回答。
- **最佳实践**：混合检索（稠密向量 + 稀疏关键词）是当前缓解检索错漏的主流做法。
- 检索质量和分块策略 > 模型大小。

### 2.6 Multi-Agent（多智能体协作）
主管–工人（Supervisor/Worker）、流水线、同行评审等拓扑。
- **适用**：子任务可并行、需要不同专长/工具集的长周期任务。
- **代价**：协调复杂度高，本质是分布式系统问题（失败隔离、心跳、超时）。**除非单 agent 明确不够，否则不要上**。

## 3. 记忆三层架构

| 层 | 作用域 | 存储 | 示例 |
|---|---|---|---|
| Working（工作记忆） | 当前对话 | 上下文窗口 | ReAct 轨迹、最近消息 |
| Episodic（情景记忆） | 历史交互 | 向量库 | "这个群上次报错是 XX 问题"、"用户偏好简短回复" |
| Semantic（语义记忆） | 世界知识 | RAG 管道 | 产品文档、日志模式知识库、历史工单 |

要点：上下文窗口有限 → 需要**淘汰/摘要策略**（防"lost in the middle"）；长期记忆要有**边界与驱逐策略**，防止上下文污染。

## 4. MCP（Model Context Protocol）

2024 年底发布，到 2026 年已成为模型连接外部工具/数据的事实标准（"AI 的 USB-C"）。
- 三原语：**Tools**（可执行函数）、**Resources**（只读数据）、**Prompts**（模板）。
- C# 生态原生支持（ModelContextProtocol NuGet）。把内部系统包成 MCP server，接口稳定、可复用。

## 5. .NET / C# 生态选型

| 场景 | Semantic Kernel (SK) | Microsoft Agent Framework (MAF) |
|---|---|---|
| 简单单轮功能 | ✅ 理想 | 过度设计 |
| 多轮对话+工具 | ✅ 可用 | ✅ 更优（未来方向） |
| 多智能体协作 | ⚠️ 有限 | ✅ 为此而生（图编排、handoff） |
| 长任务 / human-in-the-loop | ❌ | ✅ 会话状态管理 |

- **SK**：插件模型（DI + 接口 + `[Description]` 特性）、prompt 模板、多 provider 连接器、记忆管理。生产实践：`MaximumAutoInvokeAttempts` 防死循环、CancellationToken 贯穿、插件可独立单测。
- **MAF 1.0**（2026-04 发布）：稳定 API、长期支持、中间件管线（审批/校验/限流 guardrails）、原生 MCP 互操作。
- **策略**：**以 SK 包为基础起步，面向 MAF API 设计**——新项目直接对准 MAF，SK 做底层插件/连接器层。

## 6. 工程化原则（决定 demo 与产品的差距）

1. **明确终止条件**与硬性迭代上限，防失控循环和成本爆炸。
2. **工具 schema 质量 > 模型选择**：清晰参数类型、真实示例、使用时机说明。
3. **可观测性**：每个 thought/action/observation 都要可记录、可检查。没有 trace 就无法调试 agent。步骤级遥测：时长、token、工具错误率、检索质量、计划遵循度。
4. **Guardrails 在 harness 层强制**，不指望模型自觉：成本上限、速率限制、敏感操作人工确认。
5. **安全**：prompt 注入是真实风险（OWASP LLM01/LLM06）——工具输出视为不可信输入；最小权限；破坏性操作 human-in-the-loop。
6. **评估（Evals）**：从第一天就建结构化测试集，度量真实任务成功率，否则迭代全靠肉眼。
7. **幂等与重试**：工具调用要幂等，配退避策略和死信处理，防级联故障。

## 7. 模式组合的典型形态

一个生产级系统几乎从不单用一种模式，典型组合：
**Plan-Execute（顶层拆解）→ ReAct（每步执行）→ Reflection（每步校验）→ Memory（跨会话持久）→ RAG（知识接地）**。

选择顺序的建议：
- 任务短且顺序 → ReAct 起步；
- 步骤多且相互依赖 → 加 Plan-Execute；
- 质量敏感 → 加 Reflection；
- 需要跨会话 → 加记忆；
- 需要专长/并行 → 才上 Multi-Agent。

## 8. 对 logagent-for-qq 的映射结论

| 本项目需求 | 采用的模式 |
|---|---|
| QQ 群消息上下文分析 | ReAct + 情景记忆（群会话摘要） |
| 日志智能分析 | Plan-Execute（拆解分析计划）+ Reflection（结论校验）+ 工具（解析器/统计/检索） |
| 自助学习（用户回答积累） | Episodic → Semantic 的沉淀管道 + Reflection（去噪） |
| 网站访问获取信息 | Agentic RAG（网页抓取作为工具，检索循环） |
| 知识库管理 | RAG（混合检索：向量 + 关键词） |
| 多模型分流 | 路由层（任务分类 → 模型策略 → 故障切换） |
